1.1 O que o usuário vai anexar
------------------------------
O usuário vai anexar DUAS imagens nesta conversa:

  IMAGEM 1 — "TELA PRINCIPAL / ORIGINAL"
    É a tela que aparece quando o app está em uso (a live rodando).
    É a referência PRIMÁRIA de layout, posição, tamanho, hierarquia, cores,
    ícones, espaçamento e profundidade de TODA a tela AO VIVO.
    Atenção especial obrigatória a:
      - todos os botões do lado DIREITO da tela, tanto os de CIMA quanto os
        de BAIXO;
      - o bloco superior (avatar, nome, título da live, selo AO VIVO,
        contador de espectadores);
      - o bloco inferior (campo de comentário, barra de ações, navegação);
      - a forma como o vídeo/câmera ocupa o fundo (full-bleed? recortado?
        com gradiente? com bordas arredondadas?).

  IMAGEM 2 — "COMENTÁRIOS + ESPECTADORES"
    É referência EXCLUSIVA para dois pontos:
      (a) APARÊNCIA VISUAL E TÉCNICA DOS COMENTÁRIOS:
          como cada comentário é desenhado, tipografia, cores, opacidade,
          fundo, alinhamento, espaçamento entre linhas, largura máxima,
          altura de cada item, posição vertical na tela, quantidade visível,
          fade/scroll, formato do nome do autor, formato do texto.
      (b) VISUAL ESTÉTICO DO CONTADOR DE ESPECTADORES:
          formato do badge, ícone, tipografia, cor, opacidade, formato do
          número (ex.: "1,2 mil" / "1.234" / "12,4K"), posição relativa.
    A IMAGEM 2 NÃO deve ser usada para redesenhar o resto da tela.

1.3 Como medir as imagens (processo obrigatório)
------------------------------------------------
Não use "olhômetro". Faça engenharia reversa numérica.

PASSO 1 — Dimensione a imagem
  Abra a imagem e anote a resolução real em pixels (largura x altura).
  Ex.: 1080 x 2400.

PASSO 2 — Descubra o fator de conversão
  O app será desenhado em dp. A conversão é proporcional à largura:
      dp = px_na_imagem * (LARGURA_REF_DP / LARGURA_IMAGEM_PX)
  onde LARGURA_REF_DP = 411f (ver seção 4.3).
  Ex.: elemento com 216 px de largura numa imagem de 1080 px ->
       216 * (411 / 1080) = 82,2 dp.

PASSO 3 — Preencha a MATRIZ DE MEDIDAS (obrigatória)
  Crie a tabela abaixo e preencha TODOS os elementos visíveis da IMAGEM 1.
  Ela deve ser entregue dentro do `DOCUMENTACAO_StudioLive.txt` (seção 11
  desse documento), porque é ela que permite uma IA futura reconstruir
  qualquer coisa sem adivinhar.

  +----+----------------------+------+------+--------+--------+--------+--------+--------+-------------+
  | #  | Elemento             |  X   |  Y   | Larg.  | Alt.   |  Raio  |  Cor   | Alfa   | Observações |
  |    |                      | (px) | (px) |  (px)  | (px)   |  (dp)  | (hex)  |  (%)   |             |
  +----+----------------------+------+------+--------+--------+--------+--------+--------+-------------+
  | 01 | Avatar               |      |      |        |        |        |        |        |             |

PASSO 4 — Amostre as cores
  Use conta-gotas na imagem. Anote o HEX de cada superfície e de cada texto.

  extraídos da imagem — não com cores "parecidas".

PASSO 5 — Converta tudo para dp e registre em `DesignTokens.kt`
  Nenhum número mágico solto no meio de um Composable. Todos os valores

1.4 Critério objetivo de "100% fiel"
------------------------------------
Considere fiel quando, colocando o app ao lado da IMAGEM 1 no mesmo tamanho
de tela, for possível responder "sim" a TODAS estas perguntas:
  [ ] Os mesmos elementos existem, na mesma ordem?
  [ ] Cada elemento está na mesma posição relativa (+-2 dp)?
  [ ] Os tamanhos batem (+-2 dp)?
  [ ] As cores batem (delta de canal < 6/255)?
  [ ] Os raios de canto batem (+-2 dp)?
  [ ] As opacidades de fundo batem (+-5%)?
  [ ] A tipografia tem o mesmo peso, tamanho relativo e alinhamento?
  [ ] Os ícones são os mesmos (ou equivalentes visuais inequívocos)?
  [ ] A hierarquia visual (o que chama atenção primeiro) é a mesma?
  [ ] Não há NENHUM texto em inglês visível?

4. DISPOSITIVO ALVO — MOTOROLA G84 5G (ÚNICO ALVO)
================================================================================

4.1 Especificações de referência
--------------------------------
  Modelo............: Motorola Moto G84 5G (XT2347)
  Tela..............: 6,55" pOLED, FHD+
  Resolução.........: 1080 x 2400 px
  Proporção.........: 20:9
  Densidade.........: ~402 ppi
  Densidade lógica..: tipicamente 2,625x (bucket xxhdpi / 420 dpi)
  Orientação do app.: RETRATO, travada (portrait)
  Câmera frontal....: furo (punch-hole) CENTRALIZADO no topo
  Borda.............: edge-to-edge (conteúdo desenha atrás da status bar)
  Navegação.........: gestos (barra de navegação fina) OU botões virtuais

4.2 Implicações obrigatórias
----------------------------
  - NUNCA desenhe conteúdo importante em cima do furo central da câmera.
  - Use `WindowInsets` (statusBars, navigationBars, displayCutout) para
    posicionar os blocos. Nada de padding fixo tipo "top = 50.dp".
  - O app é RETRATO. Não implemente layout de paisagem.
  - O preview da câmera deve preencher a tela inteira (full-bleed),
    com `PreviewView` em `ScaleType.FILL_CENTER` (equivalente a centerCrop).
  - Todo teste visual deve ser feito nessa proporção 20:9.

4.3 Largura de referência em dp
-------------------------------
  Se o aparelho reportar densidade 2,625x:
      1080 / 2,625 = 411,4 dp  ->  411 x 914 dp
  Se reportar 2,75x (possível em algumas ROMs):
      1080 / 2,75  = 392,7 dp  ->  393 x 873 dp

  ADOTE COMO BASE DE PROJETO: 411 dp de largura x 914 dp de altura.
  E, OBRIGATORIAMENTE, o app deve funcionar proporcionalmente caso o
  aparelho reporte 393 dp. Para isso, todo dimensionamento horizontal
  deriva de `maxWidth` em runtime:

      val scale = maxWidthDp / 411f   // ex.: 393/411 = 0,956
      fun d(v: Float) = (v * scale).dp

  Regra: `scale` deve ser calculado em UM único lugar
  (`LiveLayoutMetrics`), nunca repetido em cada componente.

4.4 Áreas seguras (estimativas de partida — confirmar no aparelho)
------------------------------------------------------------------
  Status bar........: ~28 dp
  Câmera (punch-hole): centro do topo, ~28 dp de diâmetro, ~10 dp abaixo
                       da borda física
  Barra de navegação.: ~24 dp (gestos) ou ~48 dp (botões virtuais)
  Área útil vertical.: ~914 - 28 - 24 = ~862 dp (com gestos)

  Nenhum texto ou botão deve ficar a menos de 8 dp dessas bordas.

5. PRINCÍPIOS DO NOVO DESIGN ("icônico")
================================================================================

O usuário pediu explicitamente um visual NOVO e ICÔNICO, não um clone
genérico. Traduza isso para estas decisões:

5.1 Linguagem visual
  - Fundo = vídeo da câmera em full-bleed (não há "tela de fundo").
  - Legibilidade garantida por SCRIM: gradiente vertical preto translúcido
    no topo e na base (ver 10.6). Sem scrim, texto sobre câmera é ilegível.
  - Superfícies de controle: "glass" (preto translúcido + blur simulado por
    opacidade + borda branca de 1 dp a 12-18% de alfa).
  - Cantos: generosos, mas consistentes. Pílulas para ações de 1 linha,
    círculos para ações isoladas.
  - Ícones: outline branco puro, traço ~2 dp, 24-28 dp, nunca preenchidos
    exceto quando o estado for "ativo" (ex.: microfone mutado).
  - Cor de destaque única: MAGENTA/VERMELHO de "AO VIVO" (ver 10.1).
    Todo o resto é branco/preto/cinza.
  - Nada de sombras duras. Profundidade vem de camadas (seção 10.5).
  - Nada de emojis na UI do app como ícones de ação.

5.2 O que torna o design "icônico"
  - Um selo AO VIVO inconfundível com ponto pulsante.
  - Uma "régua de ações" vertical à direita, com ícones alinhados e
    espaçamento matemático (nunca irregular).
  - Comentários como "legendas de vídeo": sem caixa pesada, alto contraste,
    leitura instantânea.
  - Contador de espectadores discreto mas sempre legível.
  - Consistência obsessiva: o mesmo raio, o mesmo gap, a mesma espessura.

5.3 O que NÃO fazer
  - Não copiar o layout atual do projeto.
  - Não usar Material3 "default" para os botões da live (FilledButton,
    ElevatedCard etc.). A camada da live usa componentes próprios.
  - Não encher a tela de elementos. O que não estiver na imagem, não existe.

9. FLUXO DE DADOS (UNIDIRECIONAL)
================================================================================

DataStore (AppPreferences)
      │  Flow<Preferences>
      ▼
ViewModel (ConfigViewModel / LiveViewModel)
      │  StateFlow<UiState>
      ▼
Composables (estado imutável, sem lógica de negócio)
      │  eventos (onClick, onValueChange)
      ▼
ViewModel -> AppPreferences (escrita)

Regras:
  - UI nunca lê DataStore direto.
  - UI nunca guarda estado de persistência em `remember` (só estado efêmero).
  - Toda escrita é `suspend` e ocorre no `viewModelScope`.

  - Um único `StateFlow<LiveUiConfig>` alimenta o overlay inteiro.

13. MOTOR DE LAYOUT RESPONSIVO (SEM BURACOS) — OBRIGATÓRIO
================================================================================

O usuário foi explícito: ao esconder botões, NÃO pode sobrar um espaço
grande. Isso exige um layout que FLUI, não um layout de posições fixas.

13.1 Princípio
--------------
  Nenhum elemento é posicionado com offset absoluto em Y.
  Elementos são agrupados em 3 BANDAS que se recalculam:

    Banda 1 (topo)    : ancorada em `insets.top + topPadding`
    Banda 2 (meio)    : régua de ações, CENTRADA entre o fim da banda 1 e o
                        início da banda 3
    Banda 3 (base)    : ancorada em `maxHeight - insets.bottom - bottomPadding`

13.2 Cálculo (implementar em `LiveLayoutMetrics`)
-------------------------------------------------
  Dados de entrada: maxWidth, maxHeight, insets, LiveUiConfig.

  scale        = maxWidth / 411f
  topPadding   = 12.dp * scale
  sidePadding  = 12.dp * scale
  railGap      = 14.dp * scale
  itemSize     = 44.dp * scale      // ajuste para o medido na imagem
  composerH    = 48.dp * scale
  composerGap  = 10.dp * scale

  alturaGrupoTopo = alturaRealDoProfileHeader + (liveTitle ? altura : 0)
  topoFim         = insets.top + topPadding + alturaGrupoTopo

  alturaComposer  = if (showCommentComposer) composerH + composerGap else 0
  alturaLista     = if (showComments)
                        min(alturaDisponivel, maxHeight * 0.30f)
                    else 0
  baseInicio      = maxHeight - insets.bottom - bottomPadding
                    - alturaComposer - alturaLista

  bandaMeioTopo    = topoFim + 20.dp * scale
  bandaMeioBase    = baseInicio - 20.dp * scale
  alturaRegua      = nItens * itemSize + (nItens - 1) * railGap
  reguaTopo        = bandaMeioTopo +
                     ((bandaMeioBase - bandaMeioTopo) - alturaRegua) / 2

  // Proteção: nunca deixar a régua invadir as bandas.
  reguaTopo = reguaTopo.coerceAtLeast(bandaMeioTopo)

  Se `alturaRegua > (bandaMeioBase - bandaMeioTopo)`, reduza `itemSize`
  progressivamente (nunca abaixo de 36 dp) e depois permita scroll interno
  na régua. Documente esse fallback.

13.3 Consequências esperadas
----------------------------
  - Esconder 3 botões do topo: a régua do topo desce 3*(itemSize+gap)?
    NÃO — a régua é UMA coluna centrada na banda do meio. Ela apenas
    encolhe e permanece centrada, sem buraco.
  - Se a IMAGEM 1 tiver DOIS blocos separados (topo-direita e base-direita),
    cada bloco é ancorado na sua banda e cresce/encolhe para DENTRO:
      Bloco A cresce para baixo a partir do topo.
      Bloco B cresce para cima a partir da base.
    O vão entre eles absorve a diferença — sem buraco visível.
  - Desligar a lista de comentários: a base sobe, o composer fica a
    `insets.bottom + bottomPadding` da borda.
  - Desligar o composer: a lista desce até a borda inferior.
  - Desligar ambos: a régua pode se estender até a base.

13.4 Como saber qual modelo usar
--------------------------------
  Olhe a IMAGEM 1:
    - Se os botões da direita formam UMA coluna contínua  -> modelo 13.2.
    - Se formam DOIS grupos visivelmente separados        -> modelo 13.3.
  Documente no `DOCUMENTACAO_StudioLive.txt` qual foi escolhido e por quê.

13.5 Teste obrigatório de responsividade
----------------------------------------
  Faça uma tabela de combinações e verifique que não há sobreposição:
    - todos visíveis
    - só topo visível
    - só base visível
    - só comentários visíveis
    - só régua visível
    - nada visível (tela limpa: apenas câmera)
  Em "nada visível" a tela deve ficar 100% câmera, sem resquícios.
