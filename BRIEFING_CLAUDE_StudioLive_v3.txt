1. REGRA ZERO — AS DUAS IMAGENS MANDAM

1.1 PRINCÍPIO
-------------
As imagens são a especificação visual final. Este documento define a
estrutura, as regras, a arquitetura e o comportamento; as imagens definem os
NÚMEROS (posições, tamanhos, cores, raios, opacidades, ícones e ordem dos
botões).

Nunca escreva "mais ou menos assim". Meça.
Nunca use "olhômetro" para posições. Use engenharia reversa numérica.
Nunca copie o layout atual do projeto. Ele é considerado lixo visual.

1.2 PROCESSO OBRIGATÓRIO DE MEDIÇÃO
------------------------------------
PASSO 1 — Dimensione a imagem
  Anote a resolução real em pixels (largura x altura). Ex.: 1080 x 2400.
  Se for um mockup, identifique a área útil da tela do celular e meça essa
  área, não o canvas inteiro.

PASSO 2 — Descubra o fator de conversão
  O app é desenhado em dp. A conversão é proporcional à largura:

      dp = px_na_imagem * (LARGURA_REF_DP / LARGURA_IMAGEM_PX)

  Onde LARGURA_REF_DP = 411f (ver Seção 4.3).
  Exemplo: um elemento com 216 px de largura numa imagem de 1080 px:
      216 * (411 / 1080) = 82,2 dp.

PASSO 3 — Preencha a MATRIZ DE MEDIDAS
  Use o modelo do APÊNDICE A. Preencha TODOS os elementos visíveis da
  IMAGEM 1 e os elementos de comentários/espectadores da IMAGEM 2.
  A matriz preenchida deve ser copiada para dentro do
  `DOCUMENTACAO_StudioLive.txt` (não é necessário criar `docs/`).

PASSO 4 — Amostre as cores
  Use conta-gotas na imagem. Anote o HEX de cada superfície e de cada texto.
  Não use cores "parecidas". Se não houver ferramenta de amostragem, estime
  e marque com "~" e "ESTIMADO" na documentação. Nunca finja que mediu.

PASSO 5 — Converta tudo para dp e registre em `DesignTokens.kt`
  Nenhum número mágico solto no meio de um Composable. Todos os valores
  medidos moram em `core/constants/DesignTokens.kt` ou em
  `ui/live/LiveLayoutMetrics.kt`.

PASSO 6 — Tire uma "foto mental" da hierarquia
  Antes de codificar, responda por escrito:
    - O que chama atenção primeiro?
    - Qual é a ordem dos botões da direita, de cima para baixo?
    - Quais botões têm fundo? Quais são ícones soltos?
    - O vídeo é full-bleed ou tem cantos arredondados?
    - Onde começa e termina a lista de comentários?
    - O composer é pílula, retângulo ou barra?
    - O selo AO VIVO tem ponto pulsante? Qual é o formato?
    - O contador de espectadores tem ícone de olho? Qual é o formato do
      número?
  Se você não conseguir responder, a imagem não foi analisada o suficiente.

1.3 CRITÉRIO OBJETIVO DE "100% FIEL"
-------------------------------------
Considere fiel quando, colocando o app ao lado da IMAGEM 1 no mesmo tamanho
de tela, for possível responder "sim" a TODAS estas perguntas:

  [ ] Os mesmos elementos existem, na mesma ordem?
  [ ] Cada elemento está na mesma posição relativa (+-2 dp)?
  [ ] Os tamanhos batem (+-2 dp)?
  [ ] As cores batem (delta de canal < 6/255)?
  [ ] Os raios de canto batem (+-2 dp)?
  [ ] As opacidades de fundo batem (+-5%)?
  [ ] A tipografia tem o mesmo peso, tamanho relativo e alinhamento?
  [ ] Os ícones são os mesmos (ou equivalentes visuais inequívocos)?
  [ ] A hierarquia visual (o que chama atenção primeiro) é a mesma?
  [ ] A profundidade (camadas, sombras, bordas, translucidez) é a mesma?
  [ ] Não há NENHUM texto em inglês visível?
  [ ] "AO VIVO" aparece em vez de "LIVE"?
  [ ] Todos os botões clicáveis têm um toggle nas configurações?

1.4 O QUE FAZER QUANDO A IMAGEM NÃO MOSTRA ALGO
------------------------------------------------
  - Se um elemento não aparece na imagem, NÃO invente.
  - Se este documento pede um elemento que não aparece na imagem, você deve
    avaliar: o documento é uma regra de produto; a imagem é a verdade visual.
    Se o elemento for obrigatório por este documento (ex.: toggle de
    configuração), ele pode existir na tela de configurações, mas NÃO deve
    ser desenhado na live se a imagem não mostrar.
  - Se a imagem mostrar um botão que este documento não listou, ADICIONE-O
    ao inventário e crie o toggle correspondente.
  - Se a imagem mostrar um texto em inglês, o app deve exibir o equivalente
    em português (regra de idioma vence a literalidade do texto da imagem).
    Exceção: nomes próprios, apelidos, títulos digitados pelo usuário e a
    marca "StudioLive".

2.3 AUDITORIA ARQUIVO POR ARQUIVO (PROBLEMAS ENCONTRADOS)
----------------------------------------------------------

  MainActivity.kt
    - `startDestination = "home"`; não existe tela de permissões.
    - Cria `ConfigViewModel` e `LiveViewModel` separados; os dois leem a
      mesma preferência, mas não compartilham estado. Alterar o nome no
      ConfigViewModel não garante atualização imediata no LiveViewModel.
    - `dispatchKeyEvent` chama um VolumeKeyManager inerte; não é problema,
      mas não deve ser apresentado como funcionalidade ativa.
    - Não trata o botão físico "voltar" na live com confirmação.
    - Não usa `WindowInsets` de forma explícita.

  ui/home/HomeScreen.kt
    - Visual antigo, genérico, sem identidade.
    - Texto "Iniciar a live" usa "live" em inglês; o correto é "Iniciar
      transmissão" ou "Iniciar ao vivo".
    - Na pasta local, o arquivo está SEM a chave de fechamento da função
      `HomeScreen` (falta um `}`). No zip atual, a chave existe. Isso mostra
      que a pasta local e o zip podem divergir; a entrega nova deve ser
      consistente.
    - Não usa insets, não usa safe area, não tem versão responsiva.

  ui/live/LiveScreen.kt
    - Abre a câmera traseira fixa; não há troca frontal/traseira.
    - Não há controle de microfone.
    - Não há estado de câmera ligada/desligada.
    - O overlay é sempre desenhado, sem toggles.
    - Não trata permissão negada com estado elegante; apenas tenta pedir.
    - Não usa `PreviewView` com `scaleType = FILL_CENTER` explícito.
    - O `AndroidView` recria o fluxo de câmera se o composable for
      recomposto de forma agressiva; falta um controlador estável.
    - `HandleVolumeKeys()` é código morto.

  ui/live/overlay/InstagramLiveOverlay.kt
    - Layout antigo, em inglês, com offsets absolutos
      (`headerTopPadding = 50f`, `commentBottomPadding = 160f`, etc.).
    - Escala baseada em 360 dp e limitada a 1,25; não é a escala do G84
      (411 dp).
    - Textos hardcoded: "youngezee", "LIVE", "Comment", "Buy", "joined",
      "Good Morning!!!", "bought a badge", etc.
    - Contador formata "1.5k" (ponto decimal e sufixo inglês); o correto é
      pt-BR ("1,5 mil").
    - Comentários são uma lista fixa sem envio, sem scroll, sem fade
      correto, sem estados de evento em português.
    - Não há toggles; se o usuário desligar comentários no ConfigViewModel,

    - A barra inferior não tem campo editável de verdade; o "Comment" é
      apenas texto.
    - Não há confirmação de encerrar; o X chama `onNavigateBack` direto.
    - Não usa `WindowInsets`; o topo pode ficar atrás do furo da câmera.
    - Não há contador de tempo visível.
    - Não há tratamento de profundidade/camadas; tudo é desenhado em um
      `Box` com `padding` fixo.
    - O arquivo tem trechos duplicados/desalinhados de chaves e comentários
      de IA; é frágil.

  ui/live/overlay/LiveOverlayScale.kt
    - Referência de 360 dp, não 411 dp.
    - `coerceIn(0.9f, 1.25f)` distorce a proporção em telas diferentes.
    - Deve ser substituído por `LiveLayoutMetrics`.

  ui/config/ConfigScreen.kt
    - Só tem nome exibido, espectadores e quatro switches.
    - Não tem "Título da live" / "Nome da live".
    - Não tem upload/remoção de avatar.
    - Não tem preview do perfil.
    - Não tem toggles para todos os botões da live.
    - Não tem "Restaurar padrões".
    - Não tem status de permissões.

    - Não há debounce nem flush ao sair; se o app for fechado logo após

    - Textos "Live" em inglês.
    - Visual genérico, sem o novo design system.

  AndroidManifest.xml
    - Declara CAMERA, RECORD_AUDIO, FOREGROUND_SERVICE,
      FOREGROUND_SERVICE_MEDIA_PROJECTION, POST_NOTIFICATIONS.
    - Não tem `android:windowSoftInputMode="adjustResize"` na Activity; o

2.4 ERROS JÁ VISTOS (NÃO REPETIR)
----------------------------------
  1) Falta de chave `}` no fim de um Composable/arquivo -> erro de
     compilação. A `HomeScreen.kt` local está assim.
  2) Chave `}` extra no fim de um Composable -> erro de compilação.
  3) `Modifier.fillBox()` não existe -> use `fillMaxWidth`/`fillMaxSize`.
  4) Referência a flag renomeada (`FeatureFlags.enableVolumeKeys` vs
     `enableVolumeKeyInterception`) -> unresolved reference.
  5) Tema `Theme.Material3.DayNight.NoActionBar` como tema de plataforma ->
     AAPT: resource not found. Use `android:style/Theme.Material.NoActionBar`.
  6) `mipmap` ausente -> erro de recurso. Use `@drawable/ic_launcher`.
  7) Build com `-Xmx2048m` em máquina de 6 GB -> JVM crash / hs_err_pid.
  8) Texto de conversa de IA colado no fim de um .kt -> "Expecting '}'".
  9) Arquivo truncado no meio -> erros de sintaxe em cascata.
  10) Strings com encoding errado -> caracteres quebrados na UI. Use UTF-8
      em todos os arquivos.
  11) ZIP com pasta `StudioLive/` na raiz -> o workflow não encontra
      `gradlew` na raiz e falha.
  12) ZIP com barras invertidas `\` -> o Linux do GitHub Actions não
      encontra os caminhos.
  13) `gradlew` com CRLF -> o workflow roda `sed -i 's/\r$//'`, mas é
      melhor entregar LF.
  14) Dependência nova sem necessidade -> risco de build. Evite.

4. DISPOSITIVO ALVO — MOTOROLA G84 5G
================================================================================

4.1 AVISO OBRIGATÓRIO
----------------------
O APK será usado APENAS num celular MOTOROLA MOTO G84 5G. Todas as dimensões
de largura, altura, posição, raio, profundidade e tipografia devem ser
calculadas para a tela desse aparelho. O app deve funcionar bem nele e deve
ter uma adaptação proporcional mínima para o caso de a ROM reportar outra
densidade. Não é necessário suportar tablets, dobras, paisagem ou outros
celulares como alvo principal.

4.2 ESPECIFICAÇÕES DE REFERÊNCIA
---------------------------------
  Modelo............: Motorola Moto G84 5G (XT2347)
  Tela..............: 6,55" pOLED, FHD+
  Resolução.........: 1080 x 2400 px
  Proporção.........: 20:9
  Densidade.........: ~402 ppi
  Densidade lógica..: tipicamente 2,625x (bucket xxhdpi / 420 dpi)
  Orientação do app.: RETRATO, travada (portrait)
  Câmera frontal....: furo (punch-hole) CENTRALIZADO no topo
  Borda.............: edge-to-edge (conteúdo desenha atrás da status bar)
  Navegação.........: gestos (barra fina) OU botões virtuais

4.3 LARGURA DE REFERÊNCIA EM DP
--------------------------------
  Se o aparelho reportar densidade 2,625x:
      1080 / 2,625 = 411,4 dp  ->  411 x 914 dp
  Se reportar 2,75x (possível em algumas ROMs):
      1080 / 2,75  = 392,7 dp  ->  393 x 873 dp

  ADOTE COMO BASE DE PROJETO: 411 dp de largura x 914 dp de altura.
  OBRIGATORIAMENTE, o app deve funcionar proporcionalmente caso o aparelho
  reporte 393 dp. Para isso, todo dimensionamento horizontal deriva de
  `maxWidth` em runtime:

      val scale = maxWidthDp / 411f   // ex.: 393/411 = 0,956
      fun d(v: Float) = (v * scale).dp

  Regra: `scale` deve ser calculado em UM único lugar
  (`LiveLayoutMetrics`), nunca repetido em cada componente.

4.4 ÁREAS SEGURAS (ESTIMATIVAS DE PARTIDA — CONFIRMAR NO APARELHO)
------------------------------------------------------------------
  Status bar........: ~28 dp
  Câmera (punch-hole): centro do topo, ~28 dp de diâmetro, ~10 dp abaixo
                       da borda física
  Barra de navegação.: ~24 dp (gestos) ou ~48 dp (botões virtuais)
  Área útil vertical.: ~914 - 28 - 24 = ~862 dp (com gestos)

  Nenhum texto ou botão deve ficar a menos de 8 dp dessas bordas.
  Use `WindowInsets.statusBars`, `WindowInsets.navigationBars`,
  `WindowInsets.displayCutout` e `WindowInsets.ime` (para o teclado). Nunca
  use `padding(top = 50.dp)` fixo.

4.5 IMPLICAÇÕES OBRIGATÓRIAS
-----------------------------
  - NUNCA desenhe conteúdo importante em cima do furo central da câmera.
  - O app é RETRATO. Não implemente layout de paisagem.
  - O preview da câmera deve preencher a tela inteira (full-bleed), com
    `PreviewView` em `ScaleType.FILL_CENTER` (equivalente a centerCrop).
  - Todo teste visual deve ser feito na proporção 20:9 (411 x 914 dp).
  - O teclado deve subir o composer (`imePadding`), sem cobrir a régua de
    ações.
  - A barra de navegação do sistema não pode cobrir o composer nem os
    botões da base.
  - A status bar deve ser transparente; o conteúdo pode passar por baixo,
    mas os elementos interativos ficam abaixo de `insets.top`.

4.6 PROFUNDIDADE (Z) NO G84
----------------------------
  A "profundidade" visual deve ser construída em camadas, não em sombras
  exageradas:

    Z0 — preview da câmera (fundo absoluto)
    Z1 — scrims de gradiente (topo e base)
    Z2 — informações (avatar, nome, título, selo, espectadores, timer,
         comentários)
    Z3 — controles (botões, régua de ações, composer)
    Z4 — diálogos/sheets (confirmação de sair, configurações rápidas)

  Sombras (`Modifier.shadow`) só em Z4. Em Z1-Z3, a profundidade vem de:
    - fundo preto translúcido (glass);
    - borda branca de 1 dp com alfa 12-18%;
    - empilhamento de camadas;
    - gradiente de scrim.
  Nada de sombra dura, nada de elevação Material padrão nos botões da live.

4.7 TESTE DE DENSIDADE
-----------------------
  - Emular 411 x 914 dp (G84) no Preview do Compose.
  - Emular 393 x 873 dp (fallback) e verificar que nada quebra.
  - Verificar que a régua de ações não invade o furo da câmera, a status
    bar, o composer ou a navigation bar.
  - Verificar que o composer sobe com o teclado.

6.1 CONCEITO

O usuário pediu um visual NOVO e ICÔNICO, não um clone genérico. A direção

  - Nada de gradientes arco-íris. O gradiente é preto -> transparente

  - Microinterações: press scale, fade/slide, pulso do AO VIVO.

7.8 RECEITA DE "GLASS"
-----------------------

          .clip(shape)
          .background(Color.Black.copy(alpha = 0.42f))
          .border(1.dp, Color.White.copy(alpha = 0.14f), shape)
  )
  ```
  Para o composer, alfa 0.62-0.68 e borda 0.18.
  Para botões ativos (mute/câmera desligada), troque o fundo para
  `LiveMagenta.copy(alpha = 0.28f)` e a borda para
  `LiveMagenta.copy(alpha = 0.45f)`, mantendo o ícone branco.

7.9 MOVIMENTO
--------------

  - Selo AO VIVO: ponto pulsante, ciclo de 1.400 ms, alfa 1,0 <-> 0,35.
    (Se o usuário preferir estático, é um toggle nas configurações.)

    `animateContentSize` ou `AnimatedVisibility`; nunca deixe buraco.

    botão principal, se houver.

10. MOTOR DE LAYOUT RESPONSIVO (SEM BURACOS) — OBRIGATÓRIO
================================================================================

10.1 PRINCÍPIO
---------------
O usuário foi explícito: ao esconder botões, NÃO pode sobrar um espaço
grande. Isso exige um layout que FLUI, não um layout de posições fixas.

Nenhum elemento é posicionado com offset absoluto em Y. Elementos são
agrupados em 3 BANDAS que se recalculam:

  Banda 1 (topo)  : ancorada em `insets.top + topPadding`.
  Banda 2 (meio)  : régua de ações, CENTRADA entre o fim da banda 1 e o
                    início da banda 3.
  Banda 3 (base)  : ancorada em `maxHeight - insets.bottom - bottomPadding`.

10.2 DADOS DE ENTRADA
----------------------
  maxWidth, maxHeight, insets (top, bottom, ime), LiveUiConfig.

10.3 FÓRMULAS DE REFERÊNCIA (AJUSTE AOS MEDIDOS)
-------------------------------------------------
  ```
  scale        = maxWidthDp / 411f
  topPadding   = 12.dp * scale
  sidePadding  = 12.dp * scale
  railGap      = 14.dp * scale
  itemSize     = 44.dp * scale      // ajuste para o medido na imagem
  composerH    = 48.dp * scale
  composerGap  = 10.dp * scale
  bottomPad    = 10.dp * scale

  alturaGrupoTopo = alturaRealDoTopBar
                    + (infoBanner ? alturaBanner + bannerGap : 0)
  topoFim         = insets.top + topPadding + alturaGrupoTopo

  alturaComposer  = if (showCommentComposer) composerH + composerGap else 0
  alturaBaseExtra = (bottomNav ? alturaNav + baseGap : 0)
                    + (buyBar ? alturaBuyBar + baseGap : 0)
  alturaDisponivel = (maxHeight - insets.bottom - bottomPad
                      - alturaBaseExtra - alturaComposer - topoFim)
                       .coerceAtLeast(0)
  alturaLista     = if (showComments)
                        min(alturaDisponivel, maxHeight * 0.30f)
                    else 0
  baseInicio      = maxHeight - insets.bottom - bottomPad
                    - alturaComposer - alturaLista - alturaBaseExtra

  bandaMeioTopo    = topoFim + 20.dp * scale
  bandaMeioBase    = (baseInicio - 20.dp * scale)
                       .coerceAtLeast(bandaMeioTopo)
  alturaRegua      = nItens * itemSize + (nItens - 1) * railGap
  if (nItens == 0) alturaRegua = 0
  reguaTopo        = bandaMeioTopo +
                     ((bandaMeioBase - bandaMeioTopo) - alturaRegua) / 2

  // Proteção: nunca deixar a régua invadir as bandas.
  reguaTopo = reguaTopo.coerceAtLeast(bandaMeioTopo)
  ```

  `alturaBaseExtra` cobre a barra inferior e a faixa de compra quando
  visíveis; se ambas estiverem ocultas, vale 0. Sem isso, o composer e a
  lista podem ficar atrás da barra inferior.

  Se `alturaRegua > (bandaMeioBase - bandaMeioTopo)`, reduza `itemSize`
  progressivamente (nunca abaixo de 36 dp) e depois permita scroll interno
  na régua. Documente esse fallback.

10.4 MODELOS DE RÉGUA
----------------------
  MODELO A — UMA COLUNA CONTÍNUA
    Se a IMAGEM 1 mostrar os botões da direita como uma coluna contínua:
      - uma única `Column` centralizada verticalmente na banda do meio;
      - `Arrangement.spacedBy(railGap)`;
      - se não couber, scroll vertical interno com fade nas bordas.

  MODELO B — DOIS BLOCOS ANCORADOS
    Se a IMAGEM 1 mostrar dois grupos visivelmente separados (topo-direita
    e base-direita):
      - um `Column` de altura total na direita;
      - Bloco A no topo, Bloco B na base;
      - um `Spacer(Modifier.weight(1f))` entre eles;
      - cada bloco usa `Arrangement.spacedBy(railGap)` e `animateContentSize`;
      - ao esconder itens, cada bloco encolhe; o espaço entre blocos
        absorve a diferença.

  MODO COMPACTO AUTOMÁTICO (ANTI-BURACO)
    Se, após aplicar os toggles, o vão entre o último botão do Bloco A e o
    primeiro do Bloco B ficar maior que `maxGap = 96.dp * scale`, o layout
    entra em "modo compacto":
      - os blocos se fundem em uma única coluna;
      - a coluna é centralizada na banda do meio;
      - gap constante de `railGap`;
      - animação de 180 ms.
    Isso evita um buraco enorme quando o usuário desliga muitos botões.
    O modo compacto pode ser forçado pelo toggle `compact_action_rail`.
    Documente no TXT de manutenção.

10.5 CONSEQUÊNCIAS ESPERADAS
-----------------------------
  - Esconder 3 botões do topo: o Bloco A encolhe; o vão aumenta; se passar
    do limite, compacta. Nunca sobra um buraco no meio de um bloco.
  - Esconder a lista de comentários: a base sobe, o composer fica a
    `insets.bottom + bottomPad` da borda.
  - Esconder o composer: a lista desce até a borda inferior.
  - Esconder ambos: a régua pode se estender até a base.
  - Esconder todos os elementos: a tela fica 100% câmera, sem resquícios.
  - Mostrar tudo de novo: o layout se recompõe sem reiniciar.

10.6 IMPLEMENTAÇÃO RECOMENDADA
-------------------------------
  - `BoxWithConstraints` na raiz do overlay para obter `maxWidth`/`maxHeight`.
  - `LocalLiveMetrics` (`CompositionLocal`) com `scale`, `insets`, `width`,
    `height`, `isCompact`.
  - `TopBar` medido com `onGloballyPositioned` para obter a altura real,
    ou use uma altura de token + `animateContentSize`.
  - `ActionRail` com `Column(Modifier.fillMaxHeight())` e `Spacer(weight)`.
  - `AnimatedVisibility` em cada item para entrada/saída suave.
  - `animateContentSize()` nos grupos.
  - Não use `ConstraintLayout` (evita dependência nova). `Box`, `Column`,
    `Row`, `Spacer`, `weight` resolvem.
  - Não use `SubcomposeLayout` a menos que seja realmente necessário; se
    usar, documente.

10.7 TESTE OBRIGATÓRIO DE RESPONSIVIDADE
-----------------------------------------
  Faça uma tabela de combinações e verifique que não há sobreposição:
    - todos visíveis;
    - só topo visível;
    - só base visível;
    - só comentários visíveis;
    - só régua visível;
    - só composer visível;
    - nada visível (tela limpa: apenas câmera);
    - todos os toggles desligados e religados sem reiniciar.
  Em "nada visível" a tela deve ficar 100% câmera, sem resquícios.
  Ver APÊNDICE E.

10.8 INSETS E TECLADO
----------------------
  - `WindowInsets.statusBars` para o topo.
  - `WindowInsets.navigationBars` para a base.
  - `WindowInsets.displayCutout` para o furo.
  - `WindowInsets.ime` + `imePadding()` no composer.
  - Quando o teclado sobe, a lista de comentários pode encolher; a régua
    não pode ser coberta. Se necessário, esconda a régua enquanto o
    teclado está aberto (com animação) e restaure ao fechar. Documente.

10.9 PERFORMANCE
-----------------
  - Evite recompor o `AndroidView` da câmera a cada mudança de estado.
    Mantenha o `PreviewView` estável e apenas atualize o `CameraSelector`.
  - Use `remember` para o `PreviewView`, `CameraProvider`, `Executor`.

  - Não use `delay` em loop sem `isActive`; cancele no `onDispose`.

15.1 REGRA

  <uses-permission android:name="android.permission.CAMERA" />

16. ARQUITETURA, PASTAS E FLUXO DE DADOS
================================================================================

16.1 PRINCÍPIOS INEGOCIÁVEIS
-----------------------------
  1. UMA Activity (`MainActivity`). Nada de várias Activities para telas.
  2. UM estado de aplicação persistido (`AppState`) e UMA fonte de verdade
     (`AppPreferences` sobre DataStore). Nenhuma tela guarda cópia própria.
  3. A UI é burra: ela recebe `AppState` + callbacks e desenha. Ela NÃO lê
     DataStore, NÃO abre arquivo, NÃO decide regra de persistência.
  4. Fluxo unidirecional:
        evento da UI -> função do ViewModel -> repositório -> DataStore
        -> Flow -> StateFlow -> recomposição da UI
  5. Estado persistido é imutável (`data class` + `copy`). Estado efêmero
     (comentários, timer, câmera, diálogos) fica separado e documentado.
  6. Nenhum Composable depende de `Activity`, `Context` ou `CameraX` direto,
     exceto o host da câmera (`LiveCameraPreview`) e o seletor de imagem.
  7. Toda dependência externa já existe no build. Não adicione bibliotecas
     (ver 17.8).
  8. O código deve ser entendível por outra IA sem abrir o histórico do chat.
     Nomes explícitos, comentários curtos em português, zero sigilo.

16.4 FLUXO DE DADOS (DESENHO)
------------------------------
  ```
  [Usuário toca/digita]
          |
          v
  Composable chama callback (ex.: onChangeDisplayName)
          |
          v
  AppViewModel (viewModelScope.launch)
          |
          v
  AppPreferences.updateDisplayName(texto)  ->  DataStore.edit
          |
          v
  DataStore emite novo Preferences
          |
          v
  AppPreferences.stateFlow: Flow<AppState> (combine + map)
          |
          v
  AppViewModel.appState: StateFlow<AppState>
          |
          v
  MainActivity / NavHost coleta com collectAsStateWithLifecycle()
          |
          v
  Telas recebem AppState + callbacks; recomposição mínima
  ```

  Regras do fluxo:
    - Nenhum Composable chama `dataStore.edit` diretamente.
    - Nenhum Composable mantém `var nome by remember { mutableStateOf(...) }`
      como fonte de verdade. Pode manter apenas o texto em edição, e ainda
      assim sincronizado com o estado quando o campo não está em foco.
    - Toda escrita é `suspend`; se o usuário tocar duas vezes rápido, a
      última vence (DataStore serializa).
    - Erros de I/O não podem derrubar o app: `catch { emit(emptyPreferences) }`
      e um log discreto.

16.5 ESTADO PERSISTIDO x ESTADO EFÊMERO
----------------------------------------
  PERSISTIDO (DataStore; sobrevive a fechar o app):
    - nome exibido, título da transmissão, caminho do avatar;
    - modo e valor de espectadores;
    - estado do microfone (`is_mic_muted`, compartilhado entre o botão da
      live e o switch "Iniciar com microfone silenciado");
    - pulso do selo, régua compacta;
    - todos os `show_*`;
    - `permissions_asked`;
    - qualquer preferência nova.

  EFÊMERO (memória; NÃO persiste, e isso é intencional):
    - comentários da sessão e o texto do composer;
    - tempo decorrido da live;
    - câmera atual (sempre abre na frontal), flash, câmera ligada/desligada;
    - diálogos, bottom sheet, foco do campo, teclado.
    - Aviso: o mute NÃO é efêmero. O botão da live e o switch das
      configurações usam a MESMA chave `is_mic_muted`. Não crie
      `last_mic_muted` nem uma segunda fonte de verdade.

  Justificativa: o usuário quer a COMPOSIÇÃO da tela e a identidade
  persistidas; ele não quer que comentários ou o cronômetro "voltem" ao
  reabrir. Documente essa distinção no TXT de manutenção.

16.6 SEQUÊNCIA DE INICIALIZAÇÃO
--------------------------------
  1. `MainActivity.onCreate`:
       - `enableEdgeToEdge()` (ou `WindowCompat.setDecorFitsSystemWindows(false)`);
       - `WindowCompat.getInsetsController(...).isAppearanceLightStatusBars = false`;
       - `setContent { StudioLiveTheme { StudioLiveRoot() } }`.
  2. `StudioLiveRoot` obtém `val vm: AppViewModel = viewModel()`.
  3. Coleta `appState` com `collectAsStateWithLifecycle()`.
  4. Enquanto o primeiro valor não chega (`appState == null`), mostra um
     splash escuro com o nome do app. Nunca mostre a home com dados vazios
     e depois "pule" para o nome real.
  5. Decide a rota inicial:
       - se `!permissionsAsked` -> `Routes.PERMISSIONS` (primeira execução);
       - senão -> `Routes.HOME`, MESMO que alguma permissão esteja negada.
         A live mostra o estado vazio e Configurações -> Permissões permite
         revisar. Isso evita mandar o usuário de volta ao gate toda vez que
         ele escolheu "Continuar sem permissões".
  6. `PermissionsScreen` pede câmera e microfone (e notificação somente se
     o serviço de gravação for realmente usado). Ao concluir — COM OU SEM
     as permissões, desde que o usuário escolha continuar — grava
     `permissions_asked = true` e navega para HOME removendo PERMISSIONS do
     back stack. Nunca prenda o usuário na tela de permissões.
  7. `HomeScreen` mostra "Iniciar transmissão" e "Configurações".
  8. Ao iniciar: navega para LIVE, faz bind da câmera frontal, inicia timer
     e simulador de espectadores.
  9. Ao sair: diálogo de confirmação; ao confirmar, unbind, para timer e
     simulador, volta para HOME.
 10. Ao abrir Configurações: a câmera é desligada (unbind) para não
     consumir recurso; ao voltar para LIVE, rebinda no estado atual.

16.7 NAVEGAÇÃO
---------------
  Rotas (constantes em `Routes.kt`):
    "permissions"  -> PermissionsScreen
    "home"         -> HomeScreen
    "live"         -> LiveScreen
    "config"       -> ConfigScreen

  Regras:
    - `NavHost` começa em `startDestination` calculado uma única vez, após
      o primeiro estado. Não troque `startDestination` durante a composição.
    - Ao sair de PERMISSIONS: `popUpTo("permissions") { inclusive = true }`.
    - Ao entrar em LIVE: `launchSingleTop = true`.
    - Configurações podem ser abertas da HOME e da LIVE. O retorno deve
      voltar para a origem (`popBackStack()`), nunca empilhar HOME no meio.
    - O botão físico voltar:
        - em LIVE -> abre o diálogo de encerrar (não sai direto);
        - em CONFIG -> volta para a origem;
        - em HOME -> comportamento padrão (sai do app);
        - em PERMISSIONS -> comportamento padrão de sair do app; a tela
          deve oferecer "Continuar sem permissões" e "Abrir configurações".
          Nunca prenda o usuário em loop.
    - Use `BackHandler` dentro de LIVE e CONFIG, não na Activity inteira,
      para não interceptar dialog/sheet abertos.

16.8 CICLO DE VIDA E PROCESSO
------------------------------
  - `AppViewModel` é escopo de Activity. Em morte de processo, o DataStore
    restaura o persistido; o efêmero recomeça (documentado).
  - `LiveScreen` usa `LifecycleEventObserver`/`LifecycleCameraController`
    para pausar a câmera em `ON_STOP` e retomar em `ON_START`.
  - O timer usa `SystemClock.elapsedRealtime()` e um tick de 1 s apenas
    para recompor o texto; ao voltar do background, o valor é recalculado,
    não "somado" por ticks perdidos.
  - O simulador de espectadores é cancelado em `onCleared()` e ao sair da
    live. Use `while (isActive)`.
  - O decoder de avatar é cancelado se a tela sair; não atualize estado de
    um ViewModel já limpo.
  - Nunca mantenha referência estática a `Context`, `Activity`,
    `PreviewView` ou `CameraProvider`.

16.9 PONTOS DE EXTENSÃO (PARA A PRÓXIMA IA)
--------------------------------------------
  Adicionar um BOTÃO novo à live:
    1. Meça na imagem (x, y, tamanho, ícone, cor, estado ativo).
    2. Adicione `show_<nome>` em `PreferenceKeys`.
    3. Adicione o Boolean em `LiveUiConfig` com padrão explícito.
    4. Mapeie em `AppPreferences` (leitura e escrita).
    5. Adicione o item em `ActionRail` na posição exata da imagem.
    6. Adicione o switch no subgrupo correto de Configurações.
    7. Adicione a string pt-BR, o `contentDescription` e a documentação.
    8. Rode a matriz do Apêndice E.

  Adicionar uma CONFIGURAÇÃO nova:
    1. Chave + tipo + padrão em `PreferenceKeys`.
    2. Campo em `AppState` (ou `LiveUiConfig`).
    3. Leitura com fallback e escrita.
    4. UI de configuração + aplicação imediata.
    5. Teste de persistência (fechar e reabrir).
    6. Documente no manual.

  Adicionar uma TELA nova:
    1. Rota em `Routes.kt`.
    2. Composable em `ui/<nome>/`.
    3. Entrada na navegação e no botão que a abre.
    4. Tratamento de voltar.
    5. Não duplique estado: use o AppViewModel.

  Adicionar uma PERMISSÃO nova:
    1. Declare no Manifest com justificativa.
    2. Peça no contexto de uso, não na inicialização (exceto câmera/mic).
    3. Trate negado/negado para sempre.
    4. Mostre o status em Configurações.
    5. Documente o impacto.

  Adicionar uma FUNCIONALIDADE real (ex.: gravação):
    1. Crie um controlador em `domain/` ou `features/`.
    2. Não bloqueie a main thread.
    3. Registre o estado efêmero no `LiveSessionState`.
    4. Substitua o placeholder "Em breve" por UI real.
    5. Atualize o manual e remova a marcação de placeholder.

16.10 ANTI-PADRÕES PROIBIDOS
-----------------------------
  - `InstagramLiveOverlay` monolítico com 1.000 linhas.
  - Dois ViewModels escrevendo a mesma chave.
  - `remember { mutableStateOf(nome) }` como fonte de verdade.
  - `LaunchedEffect(Unit) { dataStore.data.collect { ... } }` em cada tela.
  - `GlobalScope`, `runBlocking`, `Thread.sleep`.
  - `Modifier.offset(y = 123.dp)` para posicionar blocos da live.
  - `fillMaxSize()` no overlay sem respeitar insets.
  - `CameraSelector.DEFAULT_BACK_CAMERA` fixo.
  - Texto em inglês, `contentDescription = null` em botão, ícone sem rótulo.
  - `TODO()` visível ao usuário ou botão que não faz nada sem avisar.
  - Comentários de conversa de IA dentro do código.
  - Código morto, imports não usados, flags renomeadas pela metade.

17.9 CONTRATO COM O GITHUB ACTIONS

18.3 COMO GERAR O ZIP (PARA A IA)
----------------------------------
  Opção A — linha de comando (Linux/macOS/WSL), a partir da pasta que
  contém os arquivos do projeto (não a pasta pai):
  ```
  cd StudioLive
  rm -rf build app/build .gradle .idea local.properties
  zip -r ../projeto.zip . -x "*/build/*" "*/.gradle/*" "*/.idea/*" \
      "local.properties" "*.apk" "*.jks" "*.keystore" "*.DS_Store" \
      "Thumbs.db" "*/docs/*"
  ```
  Confira:
  ```
  unzip -l ../projeto.zip | head -40
  ```
  A primeira coluna deve mostrar `gradlew`, `settings.gradle.kts`, `app/`.

  Opção B — Python (Windows/macOS/Linux):
  ```
  import os, zipfile

  ROOT = r"C:\caminho\StudioLive"
  OUT  = r"C:\caminho\projeto.zip"
  SKIP_DIRS = {"build", ".gradle", ".idea", ".git", "docs"}
  SKIP_FILES = {"local.properties", ".DS_Store", "Thumbs.db"}

  with zipfile.ZipFile(OUT, "w", zipfile.ZIP_DEFLATED) as z:
      for base, dirs, files in os.walk(ROOT):
          dirs[:] = [d for d in dirs if d not in SKIP_DIRS]
          for f in files:
              if f in SKIP_FILES or f.endswith((".apk", ".jks", ".keystore")):
                  continue
              full = os.path.join(base, f)
              rel = os.path.relpath(full, ROOT).replace("\\", "/")
              z.write(full, rel)
  ```
  O `rel` com `/` é obrigatório para o Linux do CI.

  Opção C — interface gráfica:
    - Windows: selecionar o CONTEÚDO da pasta `StudioLive` (não a pasta),
      botão direito -> "Enviar para" -> "Pasta compactada".
    - macOS: selecionar o conteúdo -> clique direito -> "Comprimir".
    - Nunca compacte a pasta `StudioLive` inteira; compacte o que está
      DENTRO dela.

20.1 KOTLIN
------------
  - Kotlin idiomático, sem Java novo.
  - `data class` para estado; `sealed interface` para eventos/resultados.
  - `val` por padrão; `var` só quando necessário.
  - Sem `!!` em código de produção, exceto quando a invariante for óbvia e
    documentada (prefira `?.let`, `requireNotNull` com mensagem).
  - Sem `lateinit` em Composable. Em controller de câmera, use `lateinit`
    apenas se o ciclo de vida garantir a inicialização; documente.
  - Sem `GlobalScope`, `runBlocking`, `Thread.sleep`.
  - Corrotinas sempre com escopo (`viewModelScope`, `rememberCoroutineScope`,
    `lifecycleScope`) e cancelamento.
  - `Flow` para dados observáveis; `StateFlow` para estado de UI.
  - `collectAsStateWithLifecycle()` nas telas, nunca `collectAsState()` puro
    quando houver lifecycle disponível.

20.2 COMPOSE
-------------
  - Um Composable público por arquivo, com o mesmo nome do arquivo.
  - Componentes pequenos; sem "Deus Composable".
  - Estado para cima (state hoisting): o Composable recebe valor + lambda.
  - `remember` só para objetos de UI/efêmeros; nunca para o estado
    persistido.
  - `LaunchedEffect` com chave correta; não use `Unit` para tudo.
  - `Modifier` sempre como primeiro parâmetro opcional, com padrão
    `Modifier`.
  - Não use `Modifier.offset` absoluto para layout da live; use bandas,
    `Column`, `Row`, `Spacer(weight)`, `Box` com alinhamento.
  - Não use `ConstraintLayout` (dependência extra) nem `SubcomposeLayout`
    sem necessidade documentada.
  - Não aninhe `Box` sem motivo; prefira `Column`/`Row`.
  - Use `WindowInsets` e `imePadding`; nunca `padding(top = 50.dp)` fixo.
  - `AnimatedVisibility`/`animateContentSize` para reflow sem buraco.
  - Todo botão com `contentDescription` em português (ou `null` apenas se
    o texto visível já descrever, e ainda assim prefira descrever).
  - Alvo de toque mínimo 48 x 48 dp.

20.3 NOMENCLATURA
------------------
  - Pacote: `com.studiolive.app`.
  - Classes: PascalCase; funções/variáveis: camelCase; constantes:
    UPPER_SNAKE_CASE.
  - Composable: PascalCase (`LiveTopBar`).
  - Callback: `onVerboSubstantivo` (`onToggleMic`, `onChangeLiveTitle`).
  - Chave de preferência: `snake_case` com prefixo `show_` para visibilidade.
  - Arquivo de chave: `PreferenceKeys.kt`, objetos `object PrefKeys`.
  - Estado: `AppState`, `LiveUiConfig`, `LiveSessionState`.
  - Nada de abreviações obscuras (`cfg`, `vm2`, `tmp`).

20.4 STRINGS E IDIOMA
----------------------
  - Zero string em inglês na UI.
  - Zero string em português hardcoded em 20 arquivos: centralize em
    `strings.xml` (recomendado) ou `StringsPtBr.kt`.
  - Nomes próprios e conteúdo digitado pelo usuário são exceção.
  - `contentDescription` em português.
  - Datas/números com `Locale("pt", "BR")` ou `NumberFormat.getNumberInstance(Locale("pt","BR"))`.
  - Vírgula decimal; "mil"/"mi"; nunca "k"/"M" em texto, salvo se a
    imagem exigir e você documentar (a regra de idioma vence).

20.5 PERSISTÊNCIA
------------------
  - Uma única instância de DataStore no app.
  - Toda chave tem tipo e padrão explícitos.
  - Toda leitura tolera ausência e erro de I/O.
  - Toda escrita é `suspend` e passa pelo repositório/ViewModel.
  - Texto: salve a cada tecla ou com debounce curto + flush em `onStop`
    (recomendação: a cada tecla para garantir o requisito; ver 14.6).
  - Avatar: salve o arquivo e o caminho; nunca a URI.
  - Nunca apague dados do usuário em migração sem confirmação.
  - Nunca use `SharedPreferences` em paralelo.

20.6 CÂMERA E ÁUDIO
--------------------
  - CameraX com `PreviewView` estável e `ScaleType.FILL_CENTER`.
  - Bind/unbind no lifecycle; nunca bind em Composable sem `DisposableEffect`.
  - Troca de câmera sem recriar Activity/PreviewView.
  - Verifique `hasCamera` antes de trocar.
  - Permissão negada -> estado vazio elegante, não crash.
  - Áudio: o app não transmite; o mute é estado visual. Não finja.
  - Não peça MediaProjection na inicialização.

20.7 PERFORMANCE
-----------------
  - Sem trabalho pesado na main thread.
  - Avatar decodificado em `Dispatchers.IO`, max 512 x 512.
  - Timer com tick de 1 s; não recomponha a tela inteira a cada tick:
    isole o texto do cronômetro em um Composable que lê o estado.
  - Lista de comentários com `LazyColumn` e chave estável.
  - Não crie milhares de corações; limite partículas.
  - Evite `animateContentSize` em listas grandes; use nos grupos da régua.
  - Cancele corrotinas no `onDispose`/`onCleared`.

20.8 TRATAMENTO DE ERRO
------------------------
  - Câmera indisponível: snackbar/toast em português + preview vazio.
  - Permissão negada: tela/estado com botão "Abrir configurações".
  - Avatar corrompido: placeholder, sem crash.
  - DataStore com erro: usar padrões, sem crash.
  - Arquivo de avatar inexistente: placeholder.
  - Nunca mostre stack trace ao usuário; log apenas em debug.

20.9 ACESSIBILIDADE
--------------------
  - Contraste mínimo 4,5:1 para texto pequeno.
  - Não comunicar estado só por cor (use ícone + texto).
  - Alvos de 48 dp.
  - Suporte a `fontScale`: teste no G84 com fonte grande; se o layout
    quebrar, ajuste com `maxLines`/ellipsis, não desligue a acessibilidade.
  - `testTag` para testes, se houver.
  - Não use emoji como ícone de ação.

20.10 PROIBIÇÕES ABSOLUTAS
---------------------------
  1.  Texto em inglês na UI.
  2.  Offset absoluto em Y para blocos da live.
  3.  Medidas baseadas em 360 dp.
  4.  Layout fixo que deixa buraco ao esconder botões.
  5.  Dois ViewModels donos do mesmo dado.
  6.  UI lendo DataStore direto.
  7.  Botão/toggle sem efeito real ou sem persistência.
  8.  Campo que parece salvar e não salva.
  9.  Câmera traseira fixa.
  10. Microfone sem botão ou com dois botões conflitantes.
  11. Avatar sem upload/remoção.
  12. Nome/título hardcoded.
  13. Permissão pedida em loop.
  14. MediaProjection na inicialização.
  15. Dependência nova sem justificativa.
  16. Alterar o workflow do GitHub Actions.
  17. Deixar `TODO()` ou código morto.
  18. Inventar que compilou/testou.
  19. Entregar zip com pasta `StudioLive/` na raiz.
  20. Entregar sem `DOCUMENTACAO_StudioLive.txt`.

23. PASSO A PASSO — SUBSTITUIR O PROJETO NO GITHUB
================================================================================

23.1 O QUE É OBRIGATÓRIO x OPCIONAL
------------------------------------
  OBRIGATÓRIO para gerar o APK:
    - substituir `projeto.zip` na raiz do repositório.

  OPCIONAL (mas recomendado para manter o código no GitHub):
    - substituir a pasta `StudioLive/` no repositório.

  O CI NÃO USA a pasta `StudioLive/`. Ele usa apenas `projeto.zip`. Se você
  substituir só o zip, o APK sai com o código novo. Se quiser que o código-
  fonte no GitHub também fique atualizado, substitua a pasta.

23.2 ANTES DE COMEÇAR
---------------------
  1. Tenha em mãos o `projeto.zip` novo.
  2. Confirme que o zip tem `gradlew` na raiz (Abra o zip e veja; não pode
     ter uma pasta `StudioLive` como primeira camada).
  3. Entre em https://github.com/MassayoshiOgawa/FakeStream
  4. Confirme que está na branch `main` (canto superior esquerdo).
  5. Se quiser, faça backup do zip antigo baixando-o antes.

23.3 SUBSTITUIR O ZIP PELA WEB (SEM TERMINAL)
----------------------------------------------
  1. No repositório, clique na aba "Code".
  2. Clique em "Add file" -> "Upload files".
  3. Arraste o novo `projeto.zip` para a área de upload.
     - Se o GitHub avisar que já existe um arquivo com esse nome, é isso
       mesmo: ele vai substituir.
     - Não renomeie para `projeto (1).zip`; o workflow espera exatamente
       `projeto.zip`.
  4. Em "Commit changes", escreva:
       "Atualiza projeto.zip para StudioLive 3.0.0"
  5. Deixe marcado "Commit directly to the main branch".
  6. Clique em "Commit changes".
  7. Confirme que o arquivo na raiz tem o tamanho/data novos.

A.1 COMO USAR
--------------
  Esta matriz é o "papel milimetrado" da reconstrução. Preencha com as
  medidas da IMAGEM 1 e da IMAGEM 2 antes de codificar. Sem ela, você vai
  chutar. Com ela, qualquer IA consegue reproduzir a tela.

  Definições:
    - Origem (0,0): canto superior esquerdo da TELA do celular, incluindo
      a status bar (não a moldura do mockup).
    - X: distância em px da borda esquerda até a borda esquerda do elemento.
    - Y: distância em px da borda superior até a borda superior do elemento.
    - W: largura em px; H: altura em px.
    - Para círculos, W = H = diâmetro.
    - Para textos, meça a caixa do texto (não a linha de base).
    - Se a imagem estiver em outra resolução, converta para a tela de
      1080 x 2400 antes de preencher.
    - Densidade de referência: 2,625 px/dp. Então:
          dp = px / 2,625
          px = dp * 2,625
    - Arredonde para o dp mais próximo (0,5 dp é aceitável).
    - Cores em HEX #RRGGBB e alfa separado (0-100%).
    - Fontes: tamanho em sp (equivalente numérico ao dp na densidade
      padrão), peso (Regular/Medium/SemiBold/Bold), espaçamento.
    - "Chave" é o toggle correspondente (Seção 9.2) ou "—".

A.4 FÓRMULAS DE CONVERSÃO
--------------------------
  ```
  scale     = larguraTelaDp / 411f
  dp(valor) = valor * scale
  pxParaDp(px) = px / 2.625f
  dpParaPx(dp) = dp * 2.625f
  ```
  Para texto:
  ```
  fontSizeSp = pxMedido / 2.625f   // depois arredonde para o sp comum
  ```
  Não use `TypedValue.applyDimension` dentro de Composable; use `.dp`/`.sp`
  e o `scale` do `LiveLayoutMetrics`.

    [ ] Cores têm HEX e alfa.

      valor real. Se limitar, documente e teste. Recomendação: NÃO limitar
      no intervalo 380-430 dp.
    - `topPadding`, `sidePadding`, `itemSize`, `railGap`, `composerHeight`,
      `composerGap`, `bottomPadding` vêm dos tokens medidos.
    - `compactRail = config.compactActionRail || (gap entre blocos >
      maxGap)`.
    - O objeto é calculado UMA vez em `BoxWithConstraints` e distribuído
      por `CompositionLocal` (`LocalLiveMetrics`).
    - Nenhum componente recalcula `scale` por conta própria.

    - `LiveScreen` NÃO recebe `Context`, `NavController` ou `AppViewModel`.
    - `LiveTopBar` não decide visibilidade: recebe `config` e usa

  ```

  ADD_VIDEO, ADD_PERSON

  específicos, ou substituí-los por `onAction`; escolha UMA forma e
  documente. Todo valor de `LiveAction` precisa de um consumidor no
  ViewModel; nenhum pode cair em `TODO()`. As ações fora da régua (fechar,
  mais opções, trocar conta, comentar, enviar, barra inferior) têm
  callbacks próprios.

D.6 Invariantes que nunca podem quebrar
----------------------------------------
  1. Existe exatamente UMA instância de DataStore.
  2. Existe exatamente UMA fonte de verdade para `displayName`, `liveTitle`,
     `avatarPath`, `viewerCount`, `viewerMode`, `isMicMuted` e toggles.
  3. Trocar um toggle na configuração reflete na live sem recriar Activity.
  4. Esconder um item não deixa espaço reservado.
  5. A lista de comentários nunca cobre a régua; a régua nunca cobre o
     composer; o composer nunca fica atrás da navigation bar.
  6. O compositor sobe com o teclado.
  7. Nenhum texto em inglês.
  8. Nenhuma permissão é pedida em loop.
  9. Nenhuma tela chama `dataStore.edit`.
 10. Fechar e reabrir mantém todas as configurações persistidas.
 11. A câmera abre na frontal e troca sem piscar.
 12. O app não crasha se a câmera/mic/avatar falharem.

-------------
  - Main: Compose, CameraX bind/unbind, leitura de estado.

  - DataStore: já usa dispatcher próprio; não envolva em `withContext(IO)`
    sem necessidade.
  - Nunca acesse `PreviewView` fora da main.

APÊNDICE H — PERGUNTAS FREQUENTES E DECISÕES
================================================================================

H.1 POR QUE 411 DP E NÃO 360 DP?
---------------------------------
  Porque o Moto G84 5G reporta ~411 dp de largura (1080 px / 2,625). O
  projeto antigo usava 360 dp, o que encolhia tudo e deixava margens
  erradas. A escala agora é `maxWidth / 411`, com fallback para 393 dp.

H.2 POR QUE NÃO USAR COIL/GLIDE PARA O AVATAR?
-----------------------------------------------
  Porque o decode manual com `BitmapFactory` + `inSampleSize` resolve,
  reduz dependências e evita risco de build. O requisito é uma foto
  redonda; não precisa de cache de rede nem de transformações complexas.

H.3 POR QUE O MICROFONE É "SIMULADO"?
--------------------------------------
  Porque o app não transmite áudio para nenhum servidor. O botão controla
  um estado visual (Mic/MicOff) e persiste a preferência "iniciar mutado".
  Não é honesto dizer que ele silencia uma transmissão real. Se um dia o
  app transmitir, o `AudioController.applyMuteToRecording()` será o ponto
  de extensão.

H.4 POR QUE OS COMENTÁRIOS NÃO PERSISTEM?
------------------------------------------
  Porque são efêmeros, como em uma live real. O usuário quer a composição
  e a identidade persistidas, não o histórico de uma sessão. Se quiser
  persistir, crie uma chave separada e documente (não faça sem pedir).

H.5 POR QUE A CÂMERA ABRE NA FRONTAL?
--------------------------------------
  Porque é uma live pessoal; a frontal é o padrão esperado. A última
  câmera não é persistida para evitar abrir na traseira sem o usuário
  querer. O botão de troca está sempre disponível (se o toggle estiver
  ligado).

H.6 POR QUE NÃO USAR ROOM/HILT?
--------------------------------
  O app tem um único conjunto de preferências e uma única sessão. DataStore
  + um ViewModel resolvem. Room/Hilt adicionam complexidade, dependências e
  risco de build sem benefício.

H.7 POR QUE NÃO USAR NAVEGAÇÃO COM VÁRIAS ACTIVITIES?
------------------------------------------------------
  Porque o estado da live (câmera, timer) se perderia e a transição
  piscaria. Uma Activity + Navigation Compose mantém o estado e o visual
  contínuo.

H.8 POR QUE O ZIP PRECISA TER O CONTEÚDO NA RAIZ?
--------------------------------------------------
  Porque o workflow faz `unzip -o projeto.zip` na raiz e espera `gradlew`
  ali. Se o zip tiver uma pasta `StudioLive/`, o CI não acha o wrapper e
  falha. Esse é o erro mais comum.

H.9 POR QUE A ASSINATURA DO APK MUDA?
--------------------------------------
  Porque o GitHub Actions gera um keystore de debug novo no runner. Cada
  run pode ter uma chave diferente. O Android recusa atualizar um app com
  assinatura diferente. Solução: desinstalar a versão antiga (perde os
  dados) ou, no futuro, fixar uma chave de debug no projeto (não é escopo).

H.10 POR QUE NÃO POSSO GIRAR A TELA?
-------------------------------------
  O app é travado em retrato por design, porque a referência é 20:9 e a
  experiência é de live vertical. Layout de paisagem não é escopo. Se o
  usuário pedir, será uma nova funcionalidade.

H.11 POR QUE ESCONDER UM BOTÃO NÃO PODE DEIXAR BURACO?
-------------------------------------------------------
  Porque o usuário foi explícito. O layout usa bandas, `weight`,
  `AnimatedVisibility` e modo compacto. Se sobrar um vão > 96 dp, a régua
  se funde em uma coluna central. Não use `Spacer` fixo no lugar do botão.

H.12 POR QUE O SELO DIZ "AO VIVO" E NÃO "LIVE"?
------------------------------------------------
  Porque o app é 100% em português do Brasil. "LIVE" é inglês. A única
  exceção é se "LIVE" fizer parte de um nome próprio/marca; não é o caso.

H.13 POR QUE O CONTADOR MOSTRA "1,2 MIL"?
------------------------------------------
  Porque a formatação é pt-BR: vírgula decimal e "mil"/"mi". "1.5k" é
  inglês. Se a IMAGEM 2 mostrar outro formato, a imagem vence para o
  visual, mas a regra de idioma vence para o texto; documente a decisão.

H.14 O QUE FAZER SE A IMAGEM MOSTRAR UM BOTÃO QUE NÃO ESTÁ NA LISTA?
---------------------------------------------------------------------
  Adicione o botão, a chave `show_*`, o campo no modelo, o switch, a ação
  (real ou "Em breve"), a string e a documentação. Não invente um botão
  que não existe na imagem.

H.15 O QUE FAZER SE A IMAGEM NÃO MOSTRAR UM BOTÃO DA LISTA?
------------------------------------------------------------
  Não desenhe na live. O toggle pode existir com padrão desligado, ou nem
  existir. O padrão deve seguir a imagem. Documente a escolha.

H.16 O QUE FAZER SE AS IMAGENS NÃO CHEGAREM?
---------------------------------------------
  Pare e peça as duas imagens (Seção 0.5). Não use o baseline histórico
  como substituto. Não entregue um layout "parecido".

H.17 O QUE FAZER SE O BUILD FALHAR?
------------------------------------
  Leia a primeira mensagem de erro, compare com a tabela 17.6, corrija a
  causa raiz. Não altere o workflow, não remova etapas, não "comente" o
  código que falha. Se não conseguir, entregue o log e seja honesto.

H.18 O QUE FAZER SE O APP FECHAR AO ABRIR A LIVE?
--------------------------------------------------
  Verifique permissão de câmera, `try/catch` no bind, existência de câmera
  frontal e se o `PreviewView` está sendo recriado. O app deve mostrar um
  estado vazio, não crashar. Teste negando a permissão.

H.19 O QUE FAZER SE O TECLADO COBRIR O COMPOSER?
-------------------------------------------------
  Confirme `adjustResize` no Manifest, `imePadding()` no composer e
  `WindowInsets.ime`. Se a régua for coberta, esconda-a enquanto o teclado
  estiver aberto (com animação) e restaure ao fechar.

H.20 COMO ADICIONAR UMA FUNCIONALIDADE REAL NO FUTURO?
-------------------------------------------------------
  Crie um controlador em `domain/` ou `features/`, estado efêmero no
  `LiveSessionState`, UI no componente, string pt-BR, permissão (se
  necessário), teste e documentação. Substitua o placeholder "Em breve"
  quando a função existir de verdade.

H.21 COMO MANTER A FIDELIDADE AO LONGO DO TEMPO?
-------------------------------------------------
  A imagem é a verdade. Toda mudança visual deve ser comparada com ela.
  Mantenha a matriz do Apêndice A atualizada e os tokens em
  `DesignTokens.kt`. Não introduza "melhorias" de design que afastem da
  imagem. Se o usuário pedir uma mudança, atualize a imagem de referência
  e o token correspondente.

H.22 POSSO USAR FONTE PRÓPRIA?
-------------------------------
  Só se o arquivo `.ttf` for incluído no zip e declarado em `res/font`.
  Fonte baixável (Google Fonts) depende de rede/Play Services e pode
  falhar. O padrão é Roboto do sistema.

H.23 POSSO USAR EMOJI NOS BOTÕES?
----------------------------------
  Não. Ícones devem ser `ImageVector`/vetor. Emoji varia por aparelho e
  quebra a fidelidade.

H.24 O QUE É "MODO COMPACTO"?
------------------------------
  É o fallback da régua quando os dois blocos ficam muito distantes após
  esconder botões. Em vez de um buraco, os blocos se fundem em uma coluna
  central. Pode ser forçado pelo toggle "Régua compacta".

H.25 O QUE É "NADA VISÍVEL"?
-----------------------------
  Todos os toggles desligados. A tela deve ficar 100% câmera, sem avatar,
  sem régua, sem composer, sem barra. É o teste final do motor responsivo.

H.26 POR QUE O TIMER CONTINUA SE ESTIVER OCULTO?
-------------------------------------------------
  Porque o tempo da live é real, independentemente de aparecer. O toggle
  controla a visibilidade, não a contagem. Ao encerrar, para.

H.27 POR QUE NÃO PERSISTIR A CÂMERA ATUAL?
-------------------------------------------
  Porque o padrão de uma live pessoal é a frontal. Persistir a traseira
  pode confundir o usuário ao reabrir. Se ele quiser, troca em um toque.

H.28 O QUE FAZER COM O `VolumeKeyManager`?
-------------------------------------------
  Manter inerte ou remover. Não interceptar volume, não apresentar como
  funcionalidade. Se mantiver, garanta que não há `TODO()` solto e
  documente que é inerte.

H.29 O QUE FAZER COM O `ScreenRecordService`?
----------------------------------------------
  Manter inerte se o botão existir; ao tocar, mostrar "Em breve". Nunca
  pedir MediaProjection na inicialização. Se não houver botão na imagem,
  pode remover o serviço e as permissões correspondentes (documente).

H.30 O QUE O USUÁRIO MAIS VAI COBRAR?
--------------------------------------
  1. Fidelidade visual à imagem.
  2. Nada de inglês.
  3. Todos os botões com toggle.
  4. Sem buracos ao esconder.
  5. Persistência real.
  6. Câmera frontal/traseira.
  7. Microfone.
  8. Nome/título/avatar editáveis.
  9. Zip que compila no Actions.
 10. Instruções claras de GitHub/APK.
